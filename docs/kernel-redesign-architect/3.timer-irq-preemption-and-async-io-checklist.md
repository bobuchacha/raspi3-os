# Timer IRQ Preemption And Async I/O Checklist

## Scope

This checklist turns the current design notes into one implementation order that can be
applied incrementally without destabilizing the kernel all at once.

The first track is true timer-IRQ-driven EL0 preemption on `virt`.
The second track is asynchronous block I/O that stops tying file loads directly to the
caller thread.

## Current Status Snapshot

- Track 1 is mostly implemented in the active tree.
- The lower-EL IRQ vector now passes `AArch64ExceptionFrame*` into `aarch64_handle_irq(...)`.
- The scheduler now has separate current-EL and lower-EL timer IRQ entrypoints.
- Thread context now carries a saved exception frame plus a resume flag so an interrupted EL0 thread can resume through `eret` from the low-level context switch path.
- The `virt` board now initializes the GICv2 timer route and rearms the architected timer IRQ source while keeping the old polled deadline as a fallback.
- Validation is still incomplete. The tree contains one real preemption path plus trace points, but the checklist should still treat end-to-end proof as pending until the dedicated workloads are rerun.
- Track 2 now has its first service layer. FAT32 exact reads can submit work to a dedicated kernel block-I/O worker and wait on `WaitReason::IO`, but the external read path still behaves synchronously and the virtio backend still serializes one in-flight request.

## Track 1. EL0 Timer IRQ Preemption

### Phase 1. IRQ Plumbing Without Behavior Change

- [x] Document the implementation order in this checklist.
- [x] Pass the saved lower-EL IRQ exception frame into the C IRQ handler.
- [x] Add one scheduler IRQ entrypoint that accepts an `AArch64ExceptionFrame*`.
- [x] Keep phase-1 behavior equivalent to today: timer bookkeeping only, no preemptive switch yet.

### Phase 2. Real Timer IRQ Source On `virt`

- [x] Split the current software-deadline timer helpers from real IRQ-backed timer helpers in `kernel/include/arch/aarch64/arch_backend.h`.
- [x] Add board bring-up for the real periodic timer IRQ path in `kernel/include/platform/board/virt/platform_backend.h`.
- [ ] Validate that the periodic timer IRQ fires reliably on `virt` without invoking the scheduler switch path.

### Phase 3. Exception-Aware Resume Model

- [x] Extend thread state so the scheduler can distinguish normal context return from exception-frame return.
- [x] Store the interrupted EL0 thread's saved exception frame in thread-owned scheduler context.
- [x] Add one low-level resume path that returns through an exception epilogue instead of `ret`.
- [x] Keep the lower-EL exception-frame resume path separate from the normal current-EL kernel-switch path.

Current implementation note:
The active tree already allows current-EL timer preemption through `Scheduler::handle_current_el_timer_irq()`. The important boundary is no longer "EL0 only" versus "EL1 never"; it is that lower-EL preemption uses the saved exception-frame handoff while current-EL kernel threads stay on the normal `CpuContext` switch path.

### Phase 4. Scheduler IRQ Decision Path

- [x] Add one scheduler entrypoint that performs timer bookkeeping and decides whether the interrupted EL0 thread should be preempted immediately.
- [x] Reuse the existing ready-queue and priority policy when selecting the next runnable thread.
- [x] Save the interrupted EL0 thread as an exception-resume candidate instead of forcing it through the normal `CpuContext`-only path.
- [x] Keep the assembly IRQ epilogue simple and let the scheduler switch path decide which thread becomes active before the vector restores registers.

Current implementation note:
`SchedulerIrqAction` stays as a single `ResumeCurrent` contract. The actual thread switch, when needed, already happens before returning to the common IRQ epilogue, and the assembly vector always restores whichever frame is live on the active kernel stack. Adding a separate "resume different thread" enum would duplicate a choice the scheduler has already made and would complicate the IRQ return path without buying new behavior.

### Phase 5. Validation

- [x] Validate timer IRQ delivery with no switch.
- [x] Validate EL0-only preemption with two user threads where one spins without syscalls.
- [ ] Validate that GWES and Explorer remain responsive while the spinner runs.
- [ ] Validate that sleep and timed wakeups still work after the IRQ path changes.

Current validation note:
On 2026-04-29, fresh headless `virt` runs captured both `/tmp/irqhandoff_preempt.log` and `/tmp/irqhandoff_solo.log`. Those logs showed repeated lower-EL timer IRQ entry traces on interrupt ID 27 before the first scheduler preemption trace appeared, which is enough to prove that the periodic timer IRQ route is live even in an early no-switch window. The same validation pass also showed one explicit `lower-el timer preemption reason=quantum-expired` trace plus the `irqhandoff.1` worker reaching `worker 1 online` and sustaining heartbeat progress while the main thread remained CPU-bound. Together, those logs prove both timer IRQ delivery without an immediate switch and real EL0 timer-driven preemption once a competing runnable peer exists.

## Track 2. Async Block I/O

### Phase 1. Service Layer Above The Existing Synchronous Driver

- [x] Add a kernel block-I/O service that owns request records, a worker thread, and completion wakeups.
- [x] Reuse `WaitReason::IO` for callers waiting on asynchronous I/O completion.
- [x] Add submit, wait, and query interfaces for file-read requests.
- [x] Keep the existing VFS, FAT32, and virtio block driver behavior unchanged in this phase.

Current implementation note:
Track 2 now has a kernel-owned service layer in `kernel/service/block_io.cpp`. The first version uses heap-backed request records plus one permanent worker thread and exposes submit, wait, query, and synchronous wrapper helpers in `kernel/include/block_io.h`. FAT32 exact reads now flow through that service, so file loads stop issuing block transactions directly from the caller thread. The remaining gaps are that the public read path still waits synchronously, teardown/cancel paths do not exist yet, and the virtio backend still owns only one shared in-flight request slot.

### Phase 2. User-Facing Integration

- [ ] Add syscall entrypoints for async file read submit and completion wait, or internally convert `readFile` to submit-plus-wait once the service is stable.
- [ ] Wake blocked callers on completion rather than inventing a user interrupt delivery model.
- [ ] Cancel or detach in-flight requests during process teardown.

### Phase 3. True Driver-Level Async Completion

- [x] Split `virtio` block submission from completion draining in `kernel/include/platform/board/virt/block_backend.h`.
- [ ] Replace local busy-poll loops with queue submission plus completion records.
- [x] Add a completion drain path callable from either a temporary poll hook or a real IRQ path.
- [ ] Integrate block completion wakeups with the async block-I/O service.

Current implementation note:
`BlockStorage` now uses separate begin-request and drain-completion helpers, and `board::Platform::poll_devices()` can call a non-blocking `BlockStorage::poll()` hook. The remaining gap is that synchronous callers still spin until completion and the backend still owns only one shared request/status slot, so this is the seam for async work rather than the finished async design.

### Phase 4. Validation

- [x] Validate asynchronous file reads with a worker-thread-backed implementation first.
- [ ] Validate multi-read concurrency without corrupting the shared virtio submission state.
- [ ] Validate that UI threads remain responsive while large assets load.
- [ ] Validate process teardown with in-flight reads.

Current validation note:
On 2026-04-30, a fresh headless `virt` boot captured `/tmp/block_io_boot.log` after FAT32 exact reads were rerouted through the new block-I/O worker service. That log showed successful startup of `core.exe`, `shell.exe`, `gwes.exe`, and `explorer.exe`, which is enough to prove that boot-time executable and DLL file reads now complete correctly through the worker-backed kernel read path.
