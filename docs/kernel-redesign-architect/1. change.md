# Kernel Restructure Plan

This document defines the changes needed to improve kernel stability as the kernel and user applications scale.

## Goals

1. Improve kernel memory management.
2. Improve application load time by removing repeated copies during image loading.
3. Remove fixed ceilings everywhere except virtual address space. Everything else should scale dynamically.
4. Add clear comments and annotations so new contributors can understand the code and algorithms quickly.
5. Prefer single-line `if` and `else` statements when that keeps the code easy to read.

## Implementation Checklist Against Current Files

This checklist maps the redesign work to the current tree so implementation can
proceed in small verifiable steps instead of broad rewrites.

### Kernel Memory

- [~] Move kernel heap growth toward the planned block-mapping path.
  Current code: `kernel/heap/heap.cpp` grows from `heap_append_growth_locked()` using `PhysicalMemory::reserve_contiguous_pages()` one growth unit at a time.
  Follow-up: introduce the planned kernel block-mapping path and move growth policy out of the allocator.
- [x] Audit persistent kernel objects that still live on the heap.
  Current code: loader metadata, user-heap tracking records, GUI surface metadata records, and GUI surface backing now use page-backed ownership in `kernel/loader/dll_loader.cpp`, `kernel/user_heap.cpp`, and `kernel/gui/gui_service.cpp`; the GUI surface registry now links those page-backed records directly instead of growing a separate heap-backed container.

### Loader

- [x] Stop allocating image backing from the kernel heap.
  Current code: `kernel/loader/dll_loader.cpp` now reserves contiguous physical pages for `LoaderImageBacking` and tracks the direct-map alias through `KernelResourceManager::track_external()`.
- [x] Reduce temporary loader copies to header parsing and validation only.
  Current code: `kernel/loader/dll_loader.cpp` now stages only packed headers for uncached loads and then reads section bytes directly into the final loader backing through `populate_image_backing_from_file()`.
  Follow-up: cached-image hits still populate from their resident cache object, so any future cache redesign can decide whether that resident full-image copy remains worthwhile.
- [x] Replace remaining heap-backed loader metadata that should become page-backed or process-owned.
  Current code: `SharedLoadedImage`, `LoadedModule`, and cached-image records now come from dedicated page-backed loader pools in `kernel/loader/dll_loader.cpp` and keep their path/name text inline.
  Follow-up: keep only short-lived parse buffers on heap and move persistent image/state ownership to the final loader object model.

### Application Heap

- [x] Keep ordinary user `malloc`, `free`, and `realloc` off syscalls.
  Current code: `applications/include/user_runtime.h`, `applications/runtime/cpp_runtime.cpp`, and `applications/runtime/ros_support.c` route ordinary allocation through `user_shared_heap_*` helpers.
- [x] Grow user heap from page faults.
  Current code: `kernel/user_heap.cpp` allocates heap metadata in-kernel and maps user pages on demand in `handle_page_fault()`.
- [x] Remove compatibility paths that still expose syscall-era allocation entry points when no longer needed.
  Current code: `applications/include/app/kernel.h` now routes the legacy helper names directly to `user_shared_heap_*()`, and `applications/runtime/ros_support.c` no longer exports `call_sys_malloc()` or `call_sys_free()`.

### GUI

- [~] Keep GUI limits constrained only by reserved virtual address space.
  Current code: `kernel/include/user_address_space_layout.h` reserves a virtual GUI surface arena, and `applications/apps/gwes/window.cpp` now grows retained window/compositor tables dynamically instead of capping them with `MAX_WINDOWS`.
  Follow-up: remove any remaining fixed GUI object caps in user-mode GWES helpers that are still policy limits rather than pure VA layout.
- [~] Split GWES into dedicated service, input, and window/render execution paths.
  Current code: `applications/apps/gwes/gwes.cpp` still runs client IPC handling, shared-input draining, timer pulses, z-order updates, and final present submission inside one loop.
  Follow-up: move that work into separate files and threads with one callback-driven service path for client requests, one input path for pointer/keyboard delivery, and one window/render path for retained-window mutation and present.
- [~] Remove the synthetic global `WM_TIMER` pulse from GWES and replace it with explicit per-window timers only where an application really needs one.
  Current code: `applications/apps/gwes/gwes.cpp` sends `WM_TIMER` to every live window every `10 ms` through `GWES_TIMER_PULSE_MSEC`.
  Follow-up: Windows CE and Win32 do not define one global desktop timer cadence. `SetTimer` installs per-window or thread timers, `WM_TIMER` is low priority, and the documented minimum interval is `10 ms`. Our current global pulse is therefore test scaffolding rather than WinCE behavior and should be eliminated instead of preserved.
- [x] Reduce Explorer taskbar self-inflicted repaint and foreground/layout stalls.
  Current code: `applications/apps/explorer/taskbar.cpp` now hashes the visible taskbar/menu model so timer refreshes repaint only on visible changes, and it defers menu-toggle, menu-hide, and task-activation work out of the pointer-up handler via posted messages.
- [x] Rework surface backing ownership away from heap-backed storage if the final design requires page-backed surface objects.
  Current code: `kernel/gui/gui_service.cpp` now reserves contiguous physical pages for GUI surface backing and tracks the direct-map alias through `KernelResourceManager::track_external()` before mapping those pages into GWES and client processes.
- [x] Replace static slot bitmaps with scalable registries where the ceiling is not purely virtual address space.
  Current code: `kernel/gui/gui_service.cpp` now uses intrusive registries for published shared surfaces and reserved surface spans, while the shared-input ABI publishes a runtime-sized consumer registry derived from the mapped view size instead of a fixed consumer array.

### GUI Threading Plan

- `service_thread.cpp`
  Own client request dispatch, shell-state publication, timer registration, and non-render window metadata updates.
- `input_handle.cpp`
  Own pointer and keyboard intake, translate raw input into callback-style GWES events, and keep input back-pressure isolated from window creation or z-order work.
- `window_thread.cpp`
  Own retained-window mutations that touch compositor state, dirty-region coalescing, and final present scheduling.

### GUI Timer Decision

- WinCE compatibility target: keep `WM_TIMER` semantics aligned with `SetTimer`, not with one global server pulse.
- Observed platform behavior from Microsoft timer documentation:
  - `SetTimer` installs an application-selected interval in milliseconds.
  - Intervals smaller than `10 ms` are clamped to `USER_TIMER_MINIMUM`.
  - `WM_TIMER` is posted as a low-priority queue message when that specific timer expires.
- Implementation direction:
  - remove `GWES_TIMER_PULSE_MSEC` as the blanket timer source.
  - add explicit timer registration and cancellation in `window.dll` / GWES only for windows that request it.
  - keep the shell clock and similar periodic UI updates app-owned instead of server-wide.

### GUI Callback Direction

- Every GWES thread boundary should move work through explicit callback-style event objects rather than one polling mega-loop.
- The first implementation step is to separate the code by responsibility and stop the Explorer shell from doing synchronous layout and foreground work inside pointer-up handling.
- The next implementation step is to introduce one internal event queue per GWES worker so client IPC, input delivery, and render/present requests can wake exactly the thread that owns that state.

### Naming And Style

- [ ] Reduce internal helper prefixes inside files that are no longer exported interfaces.
  Current code: several translation units, especially `kernel/loader/dll_loader.cpp` and `kernel/gui/gui_service.cpp`, still use file-global helper prefixes heavily.
- [ ] Normalize function naming toward `CamelCase` only when touching code for functional changes.
  Current code: most kernel internals still use snake_case and should be migrated opportunistically rather than in a churn-only pass.

## 1. Kernel Memory

- The kernel heap is only for `malloc`, `realloc`, and `kfree` inside kernel code.
- The kernel heap is temporary storage only. It must not be used as persistent memory or shared memory across user processes.
- Physical memory is managed in 4 KiB pages and 2 MiB blocks. The kernel must not access raw physical memory directly; it must map memory into the kernel higher-half address space first.
- The kernel heap starts at 2 MiB. When it reaches its limit, the exception handler maps another block for the kernel heap through `ResourceManagement::map_kernel_block(virtual)`.
- `ResourceManagement::map_kernel_block(virtual)` requests a block from `PhysicalMemory::allocate_block()`, maps it at the requested virtual address, and records the kernel memory usage.

## 2. Loader

- When the loader is asked to load an image (`.EXE`, `.DLL`, `.SYS`), it first check its global registry to see if those images already loaded. If so, reuse the loaded just remap to current process. Otherwise it then asks VFS for the file size.
- The loader calls `PhysicalMemory::allocate_pages(file_size)`, and physical memory management allocates enough pages to cover the image size and returns the physical address.
- The loader then allocates only the kernel heap needed to read headers and parse the image.
- If the file is invalid, the loader frees that temporary heap memory immediately.
- If the file is valid, the loader creates the process, allocates physical memory for each section, and uses VFS to read file data directly into the mapped memory.
- After the image is fully mapped, the loader starts the process as usual.

## 3. Application Heap

- Each application owns its own heap reservation.
- `malloc`, `free`, and `realloc` must not call syscalls during normal operation.
- If a page fault occurs, the kernel checks whether the faulting address belongs to the user heap reservation. If it does, `ResourceManager::allocate_memory` allocates and maps another physical page for that process, and execution continues.
- The user runtime should keep heap management small and page-fault driven.
- Do not use syscalls for ordinary user heap allocation. Let the fault handler grow the heap when needed.
- Do not map kernel-heap-backed arenas into a process unless there is a special compatibility requirement.

## 4. GUI

### Design

- GWES owns surfaces.
- GWES shares surfaces with processes through kernel API calls.
- Each window and control owns its own surface memory area, and that memory is relocated when the surface is resized.
- `gdi.dll` and `window.dll` are shared across processes. Their code runs in each process address space, while the physical image is shared once.
- Remove fixed limits such as `MAX_WINDOWS`, `MAX_SLOTS`, and similar ceilings.
- GWES stores handles for windows, icons, brushes, fonts, glyphs, bitmaps, and other GUI resources.
- Each surface should have a header that describes its size, width, height, depth, owning process ID, window handle, and related metadata, and it should be accessed through `HSURFACE`.
- GWES must not serialize pointer intake, client IPC, and final present in one loop. Input, service coordination, and window/render work should each have a dedicated owner thread and file.
- Explorer and other shell UI should repaint only when their visible model changes. Pointer-up handlers should post follow-up layout or activation work instead of performing synchronous GWES round trips inline.

## 5. Naming

- Use short but meaningful names.
- Within the same file, avoid prefixes on internal helpers. Use prefixes only for exported functions.
- Use `CamelCase` for function names.
