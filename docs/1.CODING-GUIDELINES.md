# CODING GUIDELINES

## Purpose

This document defines the coding and naming rules for the kernel codebase.

The goal is to keep the code:

- easy to read
- easy to search
- easy to maintain
- low-noise
- practical for both C and C++

This project favors clarity over cleverness.

---

## Core naming style

Use only a small number of naming forms.

### Types

Use **PascalCase** for:

- structs
- unions
- enums
- classes
- typedef names

Examples:

```c
typedef struct Thread Thread;
typedef struct Process Process;
typedef struct SpinLock SpinLock;
typedef enum ThreadState ThreadState;
```

```cpp
class Scheduler;
class PageAllocator;
struct InterruptFrame;
enum class ThreadState;
```

### Functions

Use **snake_case** for all function names in both C and C++.

Examples:

```c
void init_thread(Thread* thread);
void enqueue_thread(Thread* thread);
void map_page(VirtualMemory* vm, uintptr_t va, uintptr_t pa, uint32_t flags);
```

```cpp
class Scheduler {
public:
    void add_thread(Thread* thread);
    Thread* pick_next();
};
```

### Variables

Use **snake_case** for:

- local variables
- function parameters
- struct fields
- class fields
- global variables

Examples:

```c
Thread* current_thread;
Process* parent_process;
uint32_t page_count;
bool is_runnable;
```

### Macros

Use **UPPER_CASE** for:

- preprocessor macros
- header guards
- compile-time macro constants

Examples:

```c
#define PAGE_SIZE 4096
#define MAX_CPU_COUNT 8
#define INVALID_HANDLE 0
```

### Typed constants in C++

Use **PascalCase** for typed constants.

Examples:

```cpp
constexpr uint32_t PageSize = 4096;
constexpr uint32_t MaxCpuCount = 8;
```

This keeps typed constants visually distinct from macros without adding extra prefixes.

## Naming rules

## 1. General rules

1. Prefer full words over abbreviations.
2. Use names that describe meaning, not just type.
3. Keep names consistent across the whole project.
4. Avoid decorative prefixes and suffixes unless they add real value.
5. A reader should understand what a name means without needing surrounding comments.

Good:

```c
current_thread
parent_process
message_queue
kernel_stack
physical_address
```

Avoid:

```c
curThr
pproc
msgq
kstk
pa2
```

---

## 2. Types

All types should use PascalCase.

### C examples

```c
typedef struct Thread Thread;
typedef struct Process Process;
typedef struct MessageQueue MessageQueue;
typedef struct VirtualMemory VirtualMemory;
typedef union PageEntry PageEntry;
typedef enum ThreadState ThreadState;
```

### C++ examples

```cpp
class Scheduler;
class HeapAllocator;
struct InterruptFrame;
struct CpuContext;
enum class ThreadState;
```

### Rule

Do not use `_t`.

Avoid:

```c
thread_t
process_t
spinlock_t
```

Use:

```c
Thread
Process
SpinLock
```

---

## 3. Functions

Use snake_case for all functions.

This applies to:

- C functions
- C++ free functions
- C++ methods

Examples:

```c
void create_thread(void);
void destroy_thread(Thread* thread);
void schedule_next(void);
bool is_page_aligned(uintptr_t address);
```

```cpp
class ProcessManager {
public:
    bool create_process(const char* path);
    void destroy_process(uint32_t process_id);
};
```

### Rule

Function names should usually start with a verb.

Good:

```c
map_page
alloc_page
free_page
send_message
wait_event
lock_spinlock
unlock_spinlock
```

Avoid vague names:

```c
do_it
handle_thing
run_code
process_data
```

---

## 4. Variables and parameters

Use snake_case for all variables and parameters.

Examples:

```c
Thread* current_thread;
Thread* next_thread;
uint32_t cpu_id;
size_t buffer_size;
bool is_blocked;
uintptr_t physical_address;
```

### Boolean names

Boolean variables should read like truth statements.

Use prefixes such as:

- `is_`
- `has_`
- `can_`
- `should_`
- `was_`

Examples:

```c
bool is_ready;
bool has_message;
bool can_sleep;
bool should_yield;
bool was_signaled;
```

Avoid:

```c
bool ready;
bool flag;
bool state;
```

---

## 5. Struct and class fields

Use snake_case for fields.

Examples:

```c
struct Thread {
    uint32_t id;
    uint32_t priority;
    ThreadState state;
    void* kernel_stack;
    void* user_stack;
    Process* process;
};
```

```cpp
class Scheduler {
private:
    Thread* current_thread;
    Thread* idle_thread;
    uint32_t ready_count;
};
```

### Private fields in C++

Do not add special prefixes like `m_`.

Do not add `_` suffixes unless there is a strong reason.

Preferred:

```cpp
class Thread {
public:
    void set_priority(uint32_t priority_value) {
        priority = priority_value;
    }

private:
    uint32_t priority;
};
```

If a parameter conflicts with a member name, rename the parameter clearly.

Preferred:

```cpp
void set_state(ThreadState new_state) {
    state = new_state;
}
```

Avoid this style unless absolutely needed:

```cpp
state_ = state;
m_state = state;
```

---

## 6. Enums

Use PascalCase for enum type names.

### C enums

Use descriptive PascalCase values.

```c
typedef enum ThreadState {
    ThreadReady,
    ThreadRunning,
    ThreadBlocked,
    ThreadSleeping,
    ThreadTerminated
} ThreadState;
```

### C++ enum class

Use shorter PascalCase values because they are scoped.

```cpp
enum class ThreadState {
    Ready,
    Running,
    Blocked,
    Sleeping,
    Terminated
};
```

### Rule

Avoid old-style all-caps enum values unless there is a strong compatibility reason.

Avoid:

```c
THREAD_READY
THREAD_RUNNING
THREAD_BLOCKED
```

---

## 7. Macros

Macros must be visually obvious.

Use UPPER_CASE.

Examples:

```c
#define PAGE_SIZE 4096
#define KERNEL_BASE 0xFFFF000000000000ULL
#define MAX_THREADS 256
#define ALIGN_UP(x, a) (((x) + ((a) - 1)) & ~((a) - 1))
```

### Rules

- Prefer inline functions or `constexpr` over macros when possible.
- Use macros only when they are actually needed.
- Macro names should be short, direct, and global-safe.

---

## 8. Files

Use lowercase file names.

Use snake_case when multiple words are needed.

Examples:

```text
thread.h
thread.c
process.h
process.c
memory.h
memory.c
virtual_memory.h
virtual_memory.cpp
interrupts.h
interrupts.cpp
```

### Rules

- one subsystem per file where practical
- file name should reflect the main content
- avoid vague file names like `utils.h` unless truly unavoidable

Avoid:

```text
stuff.c
helpers.cpp
misc.h
final_code.h
```

---

## 9. Namespaces

Use lowercase names for namespaces.

Examples:

```cpp
namespace kernel
{
}

namespace kernel::memory
{
}
```

Keep namespace depth reasonable.

Prefer:

```cpp
kernel
kernel::memory
kernel::ipc
kernel::fs
```

Avoid overly deep nesting without a good reason.

---

## 10. Global variables

Global variables should be rare.

When used, still keep snake_case.

Examples:

```c
extern Thread* current_thread;
extern CpuCore* current_cpu;
extern uint64_t system_ticks;
```

### Rules

- keep globals minimal
- prefer subsystem-owned state where possible
- global names must be descriptive enough that their scope is obvious

Because this is kernel code, a plain descriptive global name is acceptable.

Avoid unnecessary prefixes like:

```c
g_current_thread
g_system_ticks
```

unless the project later decides globals need stronger visual marking.

---

## 11. Pointer naming

Do not encode pointer-ness in the name.

Good:

```c
Thread* current_thread;
char* buffer;
void* context;
```

Avoid:

```c
Thread* p_thread;
char* psz_buffer;
void* lp_context;
```

The type already shows that it is a pointer.

---

## 12. Abbreviations

Avoid abbreviations unless they are standard and obvious.

Acceptable examples:

- cpu
- mmu
- ipc
- irq
- tls
- elf
- gui

Good:

```c
cpu_id
irq_number
ipc_port
tls_base
elf_image
```

Avoid obscure abbreviations:

```c
thr_q
prc_tbl
msg_hdr2
vm_rg
```

---

## 13. Acronyms

Treat acronyms as normal words inside names.

Types:

```c
CpuCore
IpcPort
ElfImage
UsbController
MmuContext
```

Functions and variables:

```c
get_cpu_id
send_ipc_message
load_elf_image
usb_controller
mmu_context
```

Avoid inconsistent forms like:

```c
CPUCore
IPCPort
ELFImage
USBController
```

unless required by external APIs.

---

## 14. Error and status naming

Use PascalCase for status types.

Examples:

```c
typedef enum Status {
    StatusOk,
    StatusInvalidArgument,
    StatusOutOfMemory,
    StatusTimeout,
    StatusNotFound
} Status;
```

Functions may return:

```c
Status map_page(...);
Status create_process(...);
```

For C++:

```cpp
enum class Status {
    Ok,
    InvalidArgument,
    OutOfMemory,
    Timeout,
    NotFound
};
```

---

## 15. Module naming

Public functions should still reflect the subsystem they belong to.

Examples:

```c
thread_create
thread_destroy
thread_sleep

process_create
process_exit

vm_map_page
vm_unmap_page

ipc_send
ipc_receive

heap_alloc
heap_free
```

This helps searchability and prevents collisions.

### Rule

Use subsystem prefixes at the function level, not through ugly type decoration.

Good:

```c
thread_resume
process_wait
timer_start
timer_stop
```

---

## 16. Header guards

Use UPPER_CASE names based on the path or module.

Examples:

```c
#ifndef THREAD_H
#define THREAD_H
...
#endif
```

or, for larger projects:

```c
#ifndef KERNEL_MEMORY_VIRTUAL_MEMORY_H
#define KERNEL_MEMORY_VIRTUAL_MEMORY_H
...
#endif
```

If the project allows it, `#pragma once` is acceptable.

---

## 17. Formatting guidance

### Braces

Use consistent brace placement.

Recommended:

```c
if (is_ready) {
    run_thread(thread);
}
```

```cpp
class Scheduler {
public:
    void add_thread(Thread* thread);
};
```

### Spacing

- one space after keywords
- one space around operators
- no extra alignment spaces for decoration
- pointers bind to the type visually in declarations

Examples:

```c
Thread* current_thread;
const char* name;
uint32_t page_count;
```

### Line length

Prefer moderate line lengths. Break long declarations and calls cleanly.

---

## 18. Commenting

Write comments for intent, not for obvious syntax.

Good:

```c
// Switch to the next runnable thread while preserving the current context.
schedule_next();
```

Avoid:

```c
// Increment i by 1.
i++;
```

### Rules

- explain why
- explain invariants
- explain unusual hardware behavior
- do not restate obvious code

---

## 19. C and C++ interoperability

For shared headers:

- keep C-compatible declarations simple
- use `extern "C"` when needed
- do not leak unnecessary C++ syntax into C headers

Example:

```c
#ifdef __cplusplus
extern "C" {
#endif

void thread_init(Thread* thread);

#ifdef __cplusplus
}
#endif
```

## 21. What to avoid

Avoid:

- `_t` type suffixes
- `m_` member prefixes
- `g_` global prefixes unless later required
- Hungarian notation
- excessive abbreviations
- inconsistent casing
- names that hide meaning

Examples to avoid:

```c
thread_t
m_state
g_current_thread
lp_buffer
dw_flags
msgq
do_stuff
helper_function
```

---

## 22. Final style summary

### Use this

- **PascalCase** for types
- **snake_case** for functions
- **snake_case** for variables
- **snake_case** for fields
- **UPPER_CASE** for macros
- **PascalCase** for typed C++ constants
- **lowercase** namespaces
- **lowercase / snake_case** file names

### Do not use this

- `_t`
- `m_`
- `g_`
- Hungarian notation
- random abbreviations
- mixed casing styles

---

## 23. One-page rule set

1. Types use PascalCase.
2. Functions use snake_case.
3. Variables use snake_case.
4. Fields use snake_case.
5. Macros use UPPER_CASE.
6. Do not use `_t`.
7. Do not use `m_` or `g_` by default.
8. Prefer full words over abbreviations.
9. Use subsystem prefixes in function names.
10. Keep naming simple, descriptive, and consistent.

---

## 24. Example of good style

```C
typedef struct Thread Thread;
typedef struct Process Process;
typedef struct VirtualMemory VirtualMemory;

typedef enum ThreadState {
    ThreadReady,
    ThreadRunning,
    ThreadBlocked,
    ThreadSleeping,
    ThreadTerminated
} ThreadState;

struct Thread {
    uint32_t id;
    uint32_t priority;
    ThreadState state;
    Process* process;
    void* kernel_stack;
};

Status thread_create(Process* process, Thread** out_thread);
void thread_destroy(Thread* thread);
void thread_resume(Thread* thread);

Status vm_map_page(VirtualMemory* vm, uintptr_t virtual_address, uintptr_t physical_address, uint32_t flags);
Status vm_unmap_page(VirtualMemory* vm, uintptr_t virtual_address);
```

## 25. Final note

Consistency is more important than perfection.

A simple naming system used everywhere is better than a sophisticated system used inconsistently.

## 26. Documentation and annotation guidelines

Clear code is the goal, but good annotations make the system maintainable long-term—especially for kernel development where behavior is often non-obvious.

This section defines how to document:

- files
- functions
- variables
- procedures
- code blocks

---

## 26.1 File-level documentation

Every `.c`, `.h`, `.cpp`, or `.hpp` file should start with a short header comment.

```C
/*
 * File: thread.c
 * Description:
 *     Implements thread lifecycle and scheduling interaction.
 *
 * Responsibilities:
 *     - Thread creation and destruction
 *     - State transitions (ready, running, blocked)
 *     - Interaction with scheduler
 *
 * Notes:
 *     - Assumes scheduler lock is held for state transitions
 *     - Not responsible for memory allocation of stacks
 */
```

---

## 26.2 Function documentation

Every public or non-trivial function should have a comment.

```C
/*
 * create_thread
 *
 * Creates a new thread within a process.
 *
 * Parameters:
 *     process       - target process that owns the thread
 *     entry_point   - function pointer where execution begins
 *     out_thread    - output pointer to the created thread
 *
 * Returns:
 *     StatusOk on success
 *     StatusOutOfMemory if allocation fails
 *
 * Notes:
 *     - The thread is created in ThreadReady state
 *     - Caller is responsible for scheduling
 */
```

---

## 26.3 Internal / small functions

```c
// Removes a thread from the ready queue. Scheduler lock must be held.
```

---

## 26.4 Variable documentation

```C
struct Thread {
    uint32_t id;                  // unique thread identifier
    uint32_t priority;            // scheduler priority (0 = highest)
    ThreadState state;            // current execution state
    void* kernel_stack;           // base of kernel stack
    uint64_t wake_tick;           // used for sleep/wakeup timing
};
```

---

## 26.5 Procedure / flow documentation

```C
/*
 * Scheduling flow:
 * 1. Save current thread context
 * 2. Move current thread to ready queue (if still runnable)
 * 3. Select next thread from highest priority queue
 * 4. Restore next thread context
 */
```

---

## 26.6 Code block documentation

```c
// Fast path: no lock needed because only one CPU modifies this field
```

---

## 26.7 Invariants and assumptions

```C
// Invariant: thread must not be in ready queue when blocked
```

---

## 26.8 Concurrency and locking notes

```C
/*
 * Thread-safe:
 *     Yes (protected by scheduler lock)
 *
 * Locking:
 *     Caller must hold scheduler->lock
 */
```

---

## 26.9 Final rule

Good documentation should answer:

- What does this do?
- Why is it written this way?
- What assumptions must hold true?
- What can break if used incorrectly?
